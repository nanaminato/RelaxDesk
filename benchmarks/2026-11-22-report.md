## Identical 1080p codec-only input

Command: `dotnet RelaxDesk.Host.dll --codec-benchmark`. Each path gets 60 deterministic BGR32 color-band frames with a small moving square, 1920x1080, no capture, no network, no WPF. H.264 requests Main, 30fps, 8Mbps CBR, low latency/no B frame, GOP 30. This low-entropy pattern is not a representative IDE, browser or high-motion workload. Codec initialization is outside these per-frame timings. Hardware test uploads the generated pixels to the GPU; real DXGI capture would not require that upload. GPU decode timing includes conversion and WPF staging readback; software decode includes CPU color conversion.

| Path | Encode P50/P95 ms | Decode P50/P95 ms | Bytes for 60 frames | Validation |
| --- | --- | --- | --- | --- |
| Deflate Fastest baseline | 1.48 / 1.97 | 1.39 / 3.77 | 8,517,259 | Exact lossless round trip |
| Software H.264 / CPU decode | 5.46 / 6.07 | 8.31 / 9.06 | 94,554 | 60/60 decoded, sampled color-band PSNR 47.17dB |
| Hardware H.264 / GPU decode | 11.33 / 12.47 | 12.32 / 15.46 | 1,575,326 | 60/60 decoded, actual DXGI surfaces, sampled PSNR 49.96dB |

The hardware path is slower and emits more bytes than software H.264 on this input. Requested CBR does not mean different encoders emit identical padding/rate control. Do not generalize this to real desktop workloads, compare lossy H.264 to lossless Deflate as equivalent quality, or claim a GPU speedup. Capture remains blocked, so full GDI/Deflate versus DXGI/H.264 comparison remains unavailable. PSNR samples exclude moving-square/band boundaries and are not a complete text-fidelity score.

## Production Host -> shared Viewer decoder, synthetic video

Command: `scripts/benchmark-video.ps1 -Frames 300 -OutputDirectory benchmarks/2026-11-22-gpu-loopback`.

Raw results: [video.txt](2026-11-22-gpu-loopback/video.txt), [per-process CPU/GPU samples](2026-11-22-gpu-loopback/resources.json). The receiver is the same MediaDecoder used by WPF, without its UI. Real pinned TLS, pairing, console approval, one-use media binding, hardware H.264 and DXGI output decoding are used. No actual desktop captured; no remote input injected.

1280x720, 300 frames, 10.38s, 28.91 decoded fps, media bytes including application header/metadata 6.970 Mbps. TLS/TCP/IP overhead is excluded, so this is application bandwidth, not NIC bandwidth. Encode P50/P95 7.04/7.77ms; decode+readback 5.26/7.80ms; receive interval 33.79/38.31ms. Test-image generation P50/P95 2.85/5.53ms is **not capture latency**. Host media queue drops=0, depth=0 at exit. Separate control socket: 992 pings, RTT P50/P95 0.20/0.36ms, max 1.20ms. Loopback RTT is not LAN RTT or input-to-photon.

Normalized process CPU mean from external samples: receiver PID 20300 ~0.80%, host PID 31736 ~1.04%. Eight sample times per process. Report GPU counters by individual engine, not as a summed percentage: receiver peaks 3D=5%, VideoProcessing=4%, VideoDecode=3%; host peaks 3D=2%, VideoProcessing=3%, vendor-labeled VideoDecode engine=7%. We preserve the driver's engine label rather than relabeling it VideoEncode. Hardware encoder status is based on hardware MFT enumeration/device-manager acceptance/real encoded output, not the label of a performance counter.

## Actual WPF render submission

A production Viewer test window receives synthetic GPU video and exits after 60 CompositionTarget submissions. One observed run: 3.05s including startup, 19.69 submitted fps; decoder P50/P95 5.20/7.37ms, decode-to-render-submit 11.75/29.54ms, WriteableBitmap render-submit 0.54/0.74ms. Latest-frame display slot dropped 17 old decoded frames while producer sent 78. These are CPU/UI submission timestamps, not physical screen Present or input-to-photon. This test does not replace visual text review.

## Recovery and test coverage

225 portable protocol/access/binary media assertions; 227 with real Schannel loopback. Eleven ABI/metadata/color/monochrome/masked-pointer contracts. Actual production rejection tests: wrong token, wrong pin, host denial, incorrect media ticket. Actual software and GPU video sessions plus peer-close cleanup passed. A deliberately skipped media frame causes authenticated keyframe request, IDR and decoder reset; 60 frames then decode successfully. This simulates a sequence gap, not real packet loss or driver removal. Device-lost/hotplug recovery, stalled-network deadlines and a reconnect without restarting host are not validated. No persistent reconnect implementation is claimed.
