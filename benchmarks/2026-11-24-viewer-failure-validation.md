# Viewer original-failure and UI isolation validation

Baseline `c7478ce`, stable .NET 11.0.100, branch `codex/dxgi-media-pipeline`. The audit found a concrete cancellation-order defect: receiver `finally` canceled control/writer before its faulted task completed, so `WhenAny` could pick a related cancellation and lose the real decode/render error. CPU bitmap/render and post-frame UI callbacks could also throw outside controlled session teardown.

Viewer now records the first causal exception/stage using existing Core `FirstSessionFailure` before canceling other workers, catches UI callbacks, joins workers and rethrows the original cause for session policy. New local stages distinguish control/media read/write, validation, CPU/GPU decoding, renderer initialization, GPU Present, CPU bitmap submission and post-frame UI updates. Display/decode/UI errors do not trigger network retry even when typed `IOException`. Valid explicit Host termination still overrides transport EOF across independent sockets. No wire or permission change, no new capture/codec implementation and no package.

Final Release build `build/viewer-failure-reviewed-artifacts` passes with zero warnings/errors and unchanged native viewport DLL. Actual `Viewer --pipeline-failure-contracts <Host.dll> cpu-decode|cpu-submit|viewer-update` uses a real production Host, pinned TLS/approval, moving Deflate fixture, shared decoder and real WPF submissions. After at least three submissions it injects respectively `InvalidDataException`, display-side `IOException`, and a post-frame `InvalidOperationException`. Each asserts the same original exception reference, correct worker/stage/received count, specific UI notice, exactly one connection generation/no retry, restored connection interface, joined session and Host exit 0/native resources zero. All three final modes exit 0 (`build/viewer-failure-reviewed-*.txt`). This is controlled injection at production boundaries, not actual broken hardware or corrupt driver reproduction.

Regression evidence:

- Core/protocol/access/TLS **2,036** checks, terminal exit 0 (`build/viewer-failure-core.txt`); Core is unchanged by the final UI callback review.
- Normal real Host→WPF Deflate session, final reviewed build, terminal exit 0 (`build/viewer-failure-reviewed-normal.txt`).
- Actual H264 CPU decode/display and inapplicable GPU-to-CPU fallback each exit 0 (`build/viewer-failure-hardware-cpu.txt`, `build/viewer-failure-gpu-fallback.txt`) before the final UI callback catch was added; these do not validate physical Present.
- Real WPF/TCP-cut recovery, fresh pinned consent, revocation/old-input clearing, explicit Host end, denial, user cancellation, changed certificate and five-retry exhaustion pass, terminal exit 0 (`build/viewer-failure-reconnect.txt`), before the final UI callback catch. That final review adds the third dedicated callback failure test and rechecks normal CPU display.

The first build with an unassigned private test hook correctly failed warnings-as-errors; adding the actual verification assignment resolved it. No failing runtime test was waived. The reviewed callback test uses the same production Update callback used after GPU submissions, but does not exercise GPU scanout. Physical Home/NVIDIA/Intel/available AMD, occlusion/device removal, UAC/lock/held input and office performance remain unaccepted. Logs retain exception type/code/stage and exclude Viewer exception messages, credentials, input and pixels. Continue the remaining release-readiness/original-requirement audit; final unified packaging/operator tests stay deferred.
