# Android 接管原因、触控板和性能排查

日期：2026-11-28。沿用实际 LAN Host 与 SM-X510，未改变 Host 口令、信任、系统策略或捕获后端。仓库同时存在其他 Android UI/i18n 开发提交，本轮保留这些改动，不以工作区 HEAD 代表独立发布包。

## 接管退出原因

根因：连续会话在任一工作任务结束后立即取消所有任务。媒体 TLS EOF 可能早于控制 TLS 上经过校验的 `session-ended-v2`，导致接管原因丢失。

`SessionTermination.Wait` 为非控制任务的传输类失败留出最多 300ms 控制通道收尾窗口；只有真实 `RemoteSessionEndedException` 可覆盖 EOF。协议/解码错误不等待，缺失或畸形通知不伪造接管原因，用户取消仍立即生效。UI 为 `ReplacedByViewer` 明确显示“会话已被另一台设备接管”。真实断网/未收到有效终止通知时仍可能显示传输错误，这是刻意保留的正确区分。

新增 8 项终止回归：EOF 先到、控制先到、沉默超时、畸形通知、解码错误、用户取消等。真实 TLS 新增两个场景：媒体先关闭 40ms 后发有效原因，以及有效原因先于媒体关闭；保留原认证/接管/心跳场景，总计 **257** 项 TLS 回环通过。

实际 Windows Viewer 再次接管修复版 Android 后，Android 返回连接表单并显示会话终止提示，未显示 EOF。该次观察发生在将通用终止提示细化为精确接管文案之前；最终精确文案随后构建并部署，不把不同文案版本的 UI 观测混为同一份证据。

## 触控板停手跳到原点

根因：`movedSinceDown` 在抬手时清零，后续视频元数据无条件同步本地坐标。无有效指针、Host-managed 或延迟的位置（包括占位的 0,0）会覆盖本地预测，下一次相对移动便从错误位置开始。

`ViewportMapper` 现在区分本地坐标所有权与初始远端位置；本地相对/直接操作后，延迟视频位置不再回写。仅可见、具备有效位置类型、在画面边界内的远端坐标可用于初始同步；真正可见的左上角坐标在本地接管前仍有效，不是一律过滤 0,0。新会话或分辨率变化重置所有权，形状仍独立更新。旧会话排队的 UI 回调不再改写新会话光标。

新增 9 项指针回归：延迟可见位置、空指针零坐标、Host-managed、停手后再次移动、真实原点、越界和直接触控。另补 4 项统计回归，管线/视口检查从 21 增至 **34**。

最终修复包的真实 LAN 触控板复测：初始 HUD 为 `32768,32768`；相对移动 100 像素后为 `36609,32768`；停手多秒再次读取仍为 `36609,32768`；再次移动 20 像素后为 `37383,32768`，没有回到原点。没有点击、创建或修改远端文件。HUD 中的 Pointer 是本地预测的归一化坐标，不宣称由它直接测得 Host 的物理鼠标位置。

## 性能改动与实测边界

- 输出缓冲查询改为非阻塞，避免每次输出排空固定等待 4ms；静止画面仍由单独轮询排空。
- 同一显示/视频代次、尺寸与 SPS/PPS 的 IDR 恢复不再重建 MediaCodec。显示/视频代次、尺寸或参数集变化仍重建，避免旧显示的输出错误确认新显示。
- 解码耗时按输入/输出 PTS 关联到提交时间，映射最多 64 项；这是提交到输出释放的代理指标，包含轮询/调度，非实际面板上屏延迟。旧值仅测排空调用耗时，不能作前后对照。
- 修复 HUD 高频采样导致 FPS 窗口不更新、队列已排空仍显示 1、丢帧统计漏掉被清理的旧帧。每 5 秒记录不含内容/按键/凭据的 `RelaxDeskPerf`，HUD 继续独立采样，采样窗口加锁。

保留的三个真实用户工作负载快照（非受控 benchmark）在平板设备时间 13:51:12.795–13:51:22.796，相隔 10.001s：接收计数 1711→1926、输出计数 1677→1892，即接收和输出均约 **21.5 FPS**；丢帧计数均为 34（该窗口未新增），队列三个样本均为 0。阶段平滑值如下，非 P50/P95：

| 项目 | 三个快照范围 |
| --- | --- |
| 控制 RTT | 5.66–6.41ms |
| 收到帧到提交 | 1.84–2.09ms |
| 提交到解码输出释放 | 12.20–16.13ms |
| 托管堆 | 4.31–4.52MB |

另一次连接冷启动 HUD 曾报告 RTT 66.2ms、提交 95.2ms，随后下降到 RTT 23.5ms、提交 1.5ms；不能用一个稳定短窗口概括所有体验。原版连续拖动采样因 UIAutomator 等待空闲而没有取得可信的运动期 FPS，故不声称量化了速度提升。

这些数据表明在所取稳定窗口中 Android 输出跟上了收到的帧，不能据此把约 21.5 FPS 的上限归因于 .NET，也不能排除运行时/GC/调度的其他影响。实际解码器为原生硬件 `c2.exynos.h264.decoder`；尚未进行同设备、同码流、同网络和同发布配置的 Kotlin 对照。当前安装仍为 Debug APK；应继续收集 Host capture/encode、发送节拍、TCP/Wi-Fi 阻塞和发布配置数据，而不是直接换语言。Android 的低延迟解码开关依赖平台/编解码器支持：[Android MediaCodec](https://developer.android.com/reference/android/media/MediaCodec)、[低延迟解码说明](https://source.android.com/docs/core/media/low-latency-media)。
