# SM-S9380：60 FPS 丢帧定位、优化与两轮真机对照

日期：2026-11-28。本轮按用户要求改用 SM-S9380。目标是 Phase 2 的测量驱动队列/速率优化；没有宣称关闭稳定 60 FPS、物理延迟或 MSTSC 对比验收。

## 环境与范围

- 手机：Samsung SM-S9380，Android 16 / API 36，SM8750，屏幕 1080×2340（会话横屏），显示密度覆盖值 510。视频解码：`c2.qti.avc.decoder`，实际日志 `low_latency=True`。
- 手机 LAN：192.168.1.5；Windows Host：192.168.1.3:48200。直接 Wi-Fi TCP/TLS，本轮没有透明中继、延迟注入、丢包或带宽限制。
- Host 使用前轮已构建的 `out/local-host-bundle/Host/RelaxDesk.Host.exe`，版本 `0.4.2-localtest.20261128.gf00a9ad.worktree`。各组使用同一个 Host 进程和 native DLL，本轮没有修改 Host 编码或网络实现。
- 实际 Desktop Duplication，2560×1440 SDR，Intel Quick Sync 硬件 H.264；手动 60 FPS / 12 Mbps，自动画质关闭。每次 Host 均确认 generation 2 和 `accepted_setting_mask=15`。
- 源负载：相同 `build/s9380-motion/bin/Motion/release/Motion.exe`，每次从头运行同一全屏细线/运动矩形，120 秒自动关闭。通过 Windows computer-use 选择并激活对应窗口。相同运动轨迹和代码，但采集启动相位不是逐帧锁步：源运行约 20–30 秒时开始采样，均在持续动画期间截取统计窗口。
- ADB 自身也通过该手机 Wi-Fi 连接。控制与稀疏日志采集各组一致；没有独立网络整形或抓包证明无线重传率。手机末尾报告 Thermal Status 0，电量 63%、电池温度约 27.1°C；这不证明所有引擎频率恒定。

## 先测量后优化

增加 `AndroidPipelineDiagnostics`，用固定上限的环形样本记录：源时间戳间隔、接收间隔、到达间隔相对源间隔的正向超出量、Host 帧头中的采集/编码时长、解码调用、输入缓冲等待、收到至提交、提交至解码输出，以及接收/提交/输出计数、字节数、突发到达、队列峰值、配置与故障恢复次数。最多十六个阶段、每阶段 1024 样本，热路径不保留屏幕载荷，也不逐帧输出日志；每五秒输出一次 `RelaxDeskPipeline`。

A 与 B 都包含相同阶段统计。A 的二进制在改动队列前独立构建并保留，B 才改为六帧与驻留期限；没有把未加统计的旧包混作对照。

### Host 编码链路限制源帧率

各组稳定窗口末尾的 Host 编码 P50 约 19.95–20.40 ms，P95 20.91–25.15 ms；采集 P50 约 1.53–1.83 ms，P95 约 2.23–2.58 ms。源帧间隔 P50 均约 22.15–22.25 ms，已无法持续提供 16.67 ms 一帧的 60 FPS。

Host 的会话汇总进一步显示：编码链路中 MFT 输出等待 P50 约 18.5–18.8 ms，输入等待近零；GPU 颜色转换计时约 15.8 ms。编码时间包含 GPU 转换/同步和 MFT 等待，不能据此认定纯 H.264 硬件核独占二十毫秒，也不能把重叠的 GPU 与 CPU 阶段相加。GPU 占用率未测得。

### 传输/接收路径存在到帧突发

稳定窗口末尾，手机到帧间隔 P95 为 63.83 / 82.45 / 80.30 / 77.65 ms；对应到达间隔相对源间隔的正向超出量 P95 约 40.16 / 60.10 / 56.37 / 55.42 ms。间隔后多帧密集到达，两帧队列会溢出，丢弃整个依赖链并等待 IDR，损失被进一步放大。

独立的 Host 会话级汇总也记录发送阻塞：四个测量会话 send P95 为 20.26 / 27.33 / 35.31 / 25.48 ms，生产至发送队列累计丢弃 954 / 456 / 451 / 417 帧。这些是包含暖机、控制与闲置边界的整段会话数，不能当作下面六十秒窗口的损失率。它们证明发送背压也确实发生。尚未用双端抓包拆分 Wi-Fi、TCP 与 Android 接收调度各自贡献；接收间隔不是单向网络延迟，已知 Viewer 丢帧率也不是网络丢包率。

### Qualcomm 解码吞吐不是本次主要瓶颈

四组解码调用 P50 约 1.48–1.54 ms，P95 2.87–3.03 ms；输入缓冲等待 P95 约 0.38–0.43 ms。稳定窗口内等待可用输入缓冲的次数均为零，Codec 故障恢复次数均为零。提交至输出释放 P50 约 12.22–12.61 ms，表示异步流水线延迟，不是串行吞吐预算或物理扫描显示。

因此当前手机不是因为硬件解码不足而长期积压；缺少源帧及突发触发的依赖恢复才是此次观测重点。这不排除所有 .NET/JNI/调度开销，也不证明其他设备和负载都无解码瓶颈。

## 实施的优化

- Android 会话压缩帧队列由 2 改为 6，可容纳已测到的短突发；保持顺序解码与完整依赖链。
- 增加默认 50 ms 的队列驻留期限；收帧端及异步/同步出队端都检查。超过期限丢弃整个链、单独记 `DroppedExpired` 并请求新 IDR，不允许持续排队拖慢输入。
- 正常的短突发不再因两帧上限立即触发关键帧恢复；仍保留有限容量，超过容量仍恢复。最大容量仍为八帧。
- 补齐过期恰好遇到旧/重复帧时的恢复通知，避免队列已清空却漏发 IDR 请求。此小修正只影响异常过期分支；第二组 B 使用包含该修正的最终包。

此次没有用无限缓冲、降低分辨率、降低目标码率或关闭鉴权来改善数字。

## 两轮同负载真机对照

顺序为 A1 → B1 → A2 → B2。每组采集 85 秒、约五秒一次；固定跳过前两次样本，再取十二个计数间隔，即实际约六十秒。FPS 用单一 Android 单调时钟的累计计数差计算，不平均 HUD 瞬时读数。输出指解码后交给 Surface 的输出释放，不是物理上屏。

| 组别 | 实际区间 s | 收到 / 输出帧 | 接收 FPS | 输出 FPS | 已知新增丢帧 | 已知丢帧/接收 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A1：2 帧 | 60.042 | 2494 / 1890 | 41.54 | 31.48 | 603 | 24.18% |
| B1：6 帧 + 50 ms | 60.014 | 2381 / 2346 | 39.67 | 39.09 | 36 | 1.51% |
| A2：2 帧 | 60.028 | 2534 / 2487 | 42.21 | 41.43 | 48 | 1.89% |
| B2：最终优化 | 60.014 | 2612 / 2593 | 43.52 | 43.21 | 21 | 0.80% |

两轮都观察到减少额外丢帧和输出增加，但第二次基线已经明显好于第一次，不能把首轮 24.18%→1.51% 当作固定收益，也不能只挑更好的一组。此测试没有置信区间或受控无线重放，不保证每次相同提升。

稳定窗口末尾阶段样本中，收到至提交 P95 为 A1 **3.88 ms**、B1 **3.80 ms**、A2 **4.05 ms**、B2 **4.00 ms**。队列允许更多突发帧后没有观测到明显等待上升；B1 峰值到 6、B2 到 5，稳定窗口内过期丢弃均为 0。期限的异常行为由确定性契约验证，不能写成真机已经触发期限路径。阶段分位数为窗口末尾最近最多 1024 个样本，不是整段六十秒全部样本。

Host 相同负载下源帧仍约二十二毫秒一帧。因此此改动改善到帧突发容忍，**没有达到稳定 60 FPS**。继续提高上限前应针对当前 Intel GPU 转换/MFT 串行等待测量多输入在途方案，或对支持的编码实现做同源对照；本轮没有未经测量地改成复杂新编码流水线。

## 原始证据、清理与未验证项

本地原始数据：`out/android-validation/s9380-{baseline,optimized,baseline2,optimized2}.log`、对应 `*-capture.json`、`s9380-host.log`、`s9380-final-comparison.json`。本地生成动画和 Host stdio 包装器位于 `out/s9380-motion`、`out/s9380-host`，均有寿命上限；没有将账号密码写入这些脚本或报告。

最后一次正常点击断开，手机显示已断开，Host 记录 `native_live_resources=0 input_release_attempted=True`；所有测试会话均有相同清理记录。拥有的 Host 经 STOP exit 0，限时动画已退出，最终没有本轮 Host/动画进程或 48200 监听。没有新增产品端后台常驻。未提交现有工作区改动或创建发布版本。
